# Account creation and email confirmation

The user requested working Fluid account creation on 2026-10-13. This expands the earlier existing-account-only overlay while retaining its approved card, direct-page fallback, native modal, browser drafts and prompt recovery.

## Implemented behavior

- `/sign-up` and its intercepted modal share the sign-in card. The form requires an email, a password of 12–1,024 characters and a matching repeated password. Email whitespace is trimmed; password whitespace is preserved. Switching modes, submitting or unmounting clears password fields. Credentials never enter React state, browser storage, URLs, logs or error messages.
- `POST /api/auth/sign-up` accepts only email/password JSON, checks the exact configured Origin, and enforces an 8,192-byte streamed limit. New users awaiting email confirmation, obfuscated duplicate users and explicit duplicate-user provider responses receive the same minimal confirmation response. No profile metadata or client-chosen owner/redirect is accepted.
- `POST /api/auth/resend-confirmation` accepts only an email, applies the same origin boundary with a 2,048-byte limit, and resends only signup confirmation. Its response does not reveal whether an account exists or is already confirmed. The user supplies the email again; the form does not retain it for later requests.
- Provider rate limits return a generic 429. Transport/provider outages, disabled email/signup configuration and the default SMTP service's unauthorized-recipient response return a generic 503. Other validation errors stay generic. The application does not automatically retry account creation or email sending.
- The shared provider serializes sign-up, resend, sign-in and sign-out. Pending requests retain their guard after overlay dismissal and internal navigation. A confirmation-required result does not authenticate the browser or refresh an earlier account into view. The confirmation notice persists in the provider; verification resumes after an explicit Check account, a successful sign-in, or a full-page confirmation callback. Browser drafts and pending prompts are independent and remain intact.
- The production project was freshly observed with signup enabled, email enabled and `mailer_autoconfirm=false`. Email verification remains enabled. A provider-issued immediate session is handled only when its user and session have the same identity, both are non-anonymous and both contain provider-confirmed email timestamps; the account provider still verifies identity through `/api/session` before private work appears. No confirmation setting was disabled or bypassed.

## Confirmation transport

The request-scoped server client uses the pinned `@supabase/ssr` 0.12.7 / `@supabase/supabase-js` 2.117.2 PKCE implementation. The `appendPkceFlowIdToRedirects` option attaches `sb_flow_id` to the callback URL so opening an older email does not use a newer request's verifier. This option is experimental upstream and is covered by a test using the actual installed SDK and a wholly synthetic provider transport.

The callback is `${getApplicationOrigin()}/auth/callback`. The application does not accept redirect destinations from request JSON, `Host`, forwarded headers, `next`, or provider error text. It validates a single bounded authorization code and optional bounded flow ID, exchanges them with Supabase, checks the confirmed identity, then redirects to the fixed `/sign-in?confirmation=complete` or `/sign-in?confirmation=failed` result. The 303 response uses `private, no-store`, `Vary: Cookie` and `Referrer-Policy: no-referrer`; the code and flow ID do not propagate to the next URL. Its Location includes an explicit empty fragment (`#`) so browsers cannot carry provider errors or legacy token fragments onto the sign-in page. Missing, expired, replayed or wrong-browser links show generic recovery guidance and a resend option.

New authentication transitions stage cookie writes until the result is validated. A pending signup commits only its SDK verifier writes; a successful callback or valid immediate session commits HttpOnly, SameSite=Lax session cookies, Secure in the hosted production runtime. Invalid provider results never commit staged session cookies. Each request creates a fresh client; no session/client is shared at module scope. Private APIs continue to authorize with server-verified identity and existing RLS ownership, never `user_metadata` or a signup response.

The flow expects the normal Supabase confirmation email link, `{{ .ConfirmationURL }}`, to visit Supabase verification and return a PKCE code to Fluid. It does not depend on replacing email templates with `token_hash` links. Such a custom template would require a different explicitly implemented verification endpoint. PKCE links should be opened in the browser that requested them; after confirmation on another device, an existing user can sign in with email/password.
