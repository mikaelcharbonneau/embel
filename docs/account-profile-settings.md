# Working account profile and date preferences

The Account tab saves a full name and two supported display preferences: time zone and date format. The name appears in the account menu only after a successful save. The saved date preferences affect Activity, recorded usage, and research-source dates through `BrowserLocalDate`. Other timestamps and browser-only views retain their existing display behavior. The default zone is America/Toronto and the default format uses a month name. English menus and light appearance remain fixed. Photo upload, notification, AI, billing, team, and account-deletion controls remain unavailable.

`GET /api/account/profile` verifies the current Auth user and reads only that owner's row. Email comes from the server's `auth.getUser()` result and is read-only; no email or identity claim is stored in the profile table. New and existing accounts without a row receive explicit defaults with revision zero. No signup trigger or project-creation dependency is introduced. A missing migration returns an unavailable state, not a fake profile save.

`PATCH /api/account/profile` accepts a strict 2 KiB JSON body containing an expected revision and the three supported values. It checks the configured same origin before parsing or authentication. Ownership comes only from Auth. The first write inserts an owner row; later writes atomically compare the expected revision. Conflicts return 409. Profile responses are private/no-store and never expose database error details.

The additive migration `20261013035222_account_profiles.sql` enables forced owner RLS for SELECT/INSERT/UPDATE. Authenticated clients receive SELECT plus narrow INSERT/UPDATE column grants. A private SECURITY INVOKER trigger owns revision increments and timestamps. Direct owner/version/timestamp edits and deletion are not granted. Inherited default ACLs are removed only from the two newly created objects; existing tables, roles, provider entitlements and worker permissions are unchanged. Profile values are display data and never authorization claims.

Unsaved values live only in the account-session provider's owner-bound memory. Reverification hides private values synchronously, a confirmed different owner clears them, and a confirmed sign-out clears them after the existing unsaved-edit confirmation. Same-owner verification restores retained edits. Fetches and acknowledgements have a 30-second bound and are fenced by owner and session generation. A failed or interrupted save blocks further writes until an explicit read checks the current saved state. Conflicting values remain visible side by side, with explicit “Use saved settings” or “Keep my edits” recovery. A read after a lost acknowledgement reports the current saved values and never repeats the mutation automatically.

Local verification includes isolated PostgreSQL/PGlite ownership, column grants and revision checks; API and Auth projection tests; real account/profile provider recovery tests; existing account signup and lifecycle regressions; and a dedicated synthetic browser harness. Browser fixtures are explicitly labeled, intercept every API request, and make no provider calls. These checks are not live signed-in persistence acceptance. Root coordinates the reviewed migration's live application and post-application advisors/readback.
