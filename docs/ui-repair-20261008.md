## Review correction: Home recovery lifecycle

Independent review of commit `78935799ac246e4d7bf23bd37f0a73e4d21af42b` found two reproducible gaps in the first repair:

- A confirmed account start did not retire the sign-in marker. Returning to Home reused the already-sent browser draft ID, so a newly edited prompt could silently open the prior account project.
- The header Sign in link bypassed the composer's preservation callback, and uncertain saves became editable before recovery receipts were hydrated on remount.

The correction retires the marker only after `strategy.start` confirms success (or an explicit unlocked browser-draft/new-prompt action). Pending or uncertain starts retain a durable edit fence. Restored prompts, scope, examples, inputs and dispatch stay locked until receipt checks complete; unresolved account saves remain immutable and cannot dispatch a duplicate. Legacy draft-ID-only markers consult existing local receipt metadata for a boolean fence without exposing another owner's destination. Confirmed account destinations remain available through recovery navigation. Existing original-body guards, account verification and provider admission behavior are preserved.

Header keyboard/click navigation now invokes the same prompt-preservation guard as the composer Sign in link. Genuine unsent prompts restore as editable with their original scope, and sign-in itself creates no project or job. No automatic request is introduced.

Before-correction evidence: the new unit tests failed on the retained marker and editable uncertain draft. Desktop/mobile browser checks reproduced six failures (header loss, reused request identity and editable uncertain remount in each viewport), while the existing composer-link round trip passed twice. The follow-up evidence bundle contains these failure logs, before/after PNGs and exact intercepted request bodies. Final verification and the corrected commit are recorded in that bundle.
