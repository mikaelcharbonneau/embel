See [current manual workflows and verification limits](standalone-manual-tools.md). Fresh real-account browser acceptance is still separate from intercepted browser fixtures. The implementation packet below records the original local-only increment. Its activation proposal is historical, not an instruction to replay installed migrations.

## Reused foundations and ownership

The increment reuses installed Zod, verified Supabase `getUser()` authentication, same-origin API guards, existing private response handling, immutable Naming verification, and existing RLS/SQL patterns. No new service, library, credentials, worker or provider call is introduced. Next route-handler APIs were checked against the installed Next 16.3.8 `dist/docs/01-app/03-api-reference/03-file-conventions/route.md`.

Each owner has one independent draft head per `domains`, `handles`, or `trademarks`. New shared tables are `standalone_workspaces` and immutable `standalone_workspace_revisions`. All tables enforce owner RLS and FORCE RLS. Authenticated users receive SELECT only and execute permissions on three narrow RPCs. Direct insert/update/delete, anonymous access, helper calls and existing service/worker grants are denied. Default grants on each new object are stripped, including named inherited default grantees; existing objects/privileges are not changed.

Function ACL cleanup resolves only the exact eight reviewed private helper signatures and three public RPC signatures. It uses neither prefix matching nor function names alone, so unrelated matching names and same-name overloads retain their definitions and ACLs. New objects use `CREATE`; a table or exact function-signature collision aborts the transaction, preserving the pre-existing object, permissions and data. Default ACL definitions are never altered.

The account tool's writable payload is always user input. Handles source labels and account-created declarations do not prove project ownership or provider availability. The separate `imports` envelope holds database-resolved frozen provenance. Consumers must not treat arbitrary payload labels as verified associations.

## HTTP and pure contracts

`src/domain/standalone-workspaces.ts` exports strict envelopes and response-schema factories; each feature owns its pure `account-codec.ts` / draft schema. `src/server/data/standalone-workspace-codecs.ts` is a closed server registry. No runtime registration or user-selected arbitrary codec exists.

- `GET /api/workspaces/[tool]`: `{ ownerId, workspace: null | { id, ownerId, tool, revision, payload, imports, createdAt, updatedAt } }`. Null means a successful owned lookup found no draft. Missing schema is 503, never a synthetic empty draft.
- `PUT /api/workspaces/[tool]`: `{ requestKey, expectedRevision, payload, imports }`; 0 creates, positive revisions update. `imports` is at most 30 unique `{ projectId, projectRevision, selectionId: UUID | null }` selectors. Unknown keys, owner claims and provider evidence are rejected. UUIDs canonicalize to lowercase.
- `GET /api/workspaces/imports?projectId=UUID`: `{ ownerId, source }`, where source is null for an owned saved project without a name; otherwise `{ projectId, projectRevision, projectTitle, name, selectionId, candidateId, origin }`. The origin is `project_name` or `naming_selection`. A selection requires both immutable IDs; a project name requires neither.

Mutations have a streamed 131,072-byte UTF-8 envelope bound. Domains adds a 24,000-byte payload bound; Handles/Trademarks each add 120,000. Structured fields have explicit string/array limits. The database independently enforces keys, types, bounds, canonical domain preparation, empty Handle evidence and the exact Trademark user-review key. SQL's initial JSONB representation cap allows formatting overhead; actual compact payload/envelope limits remain authoritative. Timestamp validation explicitly matches the installed Zod Gregorian calendar and 00–23/00–59 clock/offset rules; it does not rely on PostgreSQL's normalizing timestamptz cast. Declared-account URLs accept canonical ASCII platform roots/subdomains and optional numeric ports from 0 through 65535, including empty/default ports and leading zeros. Unicode/space paths, query strings and fragments remain accepted. Unvalidated IDNA/ACE or percent-encoded hostnames remain outside this conservative SQL host subset; the service additionally applies the existing total WHATWG feature validator. No invalid URL is persisted or silently dropped.

All responses use private/no-store and Vary: Cookie. Error statuses are 401 unauthenticated, 404 unavailable resource/tool, 409 revision/source/idempotency conflict, 413 body bound, 422 invalid input, and 503 unavailable integration/schema. Provider/database internals are never serialized.

Domains preparation uses the same explicit 25-character ECMAScript whitespace set as the existing trim helper. Inner seed whitespace is removed; LF still separates input lines before preparation. U+0085 is retained and cannot silently form a valid candidate. Case folding is bounded to ASCII capitals and the Kelvin sign, the characters whose JavaScript lowercase result can become ASCII; other Unicode remains subject to the existing ASCII syntax check. This preserves `I` → `i`, `K` → `k` and full-domain Kelvin inputs while rejecting a forged `İ` → `i` candidate. Empty-candidate drafts still retain unfinished Unicode input unchanged. Handles validates the raw hostname against the documented ASCII subset before case folding, preventing PostgreSQL from admitting a Unicode hostname that WHATWG would interpret differently. Mixed-case ASCII hosts and Unicode paths remain supported.

## Transactions and replay

`save_standalone_workspace` derives `auth.uid()`, validates draft/selector input, locks the owner/request key then owner/tool, and locks the owned head. The existing expected revision must match, including absence at revision 0. It appends one immutable revision and advances the head atomically. Same owner/request key plus the same tool, revision, canonical payload and selectors returns the original revision only while it is still the current head. Changed input, cross-tool reuse or replay after a later save conflicts. A committed first create whose response was lost can be retried with the original body/key without creating another head or revision.

New source imports are read on the server and selected Naming candidates pass `getVerifiedProjectName`, a read-only wrapper around the existing `CandidateVerifier` graph/algorithm replay. SQL then takes sorted SHARE locks on source project heads and independently resolves the current owned project revision/current selection. A head changed after application verification conflicts. Existing project writers take FOR UPDATE locks, so no new trust or writer bypass is introduced. PGlite establishes serialized behavior; true multi-connection lock waiting needs normal PostgreSQL acceptance.

Previously saved identical import selectors reuse that revision's frozen source metadata even if the source project later changes. No import mutates a project, selects another candidate, generates names or promotes a brand. Arbitrary unsaved Naming candidates are intentionally excluded. Clients send only selectors; source names/titles and immutable IDs are resolved from owned saved records. SQL can retain direct-RPC user claims from older Naming rows, but the service refuses to expose or accept them as imported candidate provenance unless the existing immutable Naming verifier succeeds.

## Browser memory and session integration seam

Shared client: `src/components/tools/account-standalone-client.ts`. It bounds streamed response bytes, validates strict tool payloads and exact save responses, uses same-origin/no-store requests and abort signals, and exposes only safe status messages.

`createStandaloneDraftMemory()` in `standalone-draft-memory.ts` is instantiated by the account session provider. It has `bind(account | null)`, `isCurrent(account)`, `get(account, tool)`, `set(account, tool, record)`, `subscribe`, `hasUnsaved` and `clear`. Records include baseline workspace/revision, editable payload, frozen imports, dirty/conflict flags and the exact pending save intent. The stored graph is cloned/frozen. No module global store, localStorage or sessionStorage holds private account drafts.

The shell/session integration owner must:

1. Instantiate/expose `standaloneDrafts` beside the existing project/Idea/Identity stores.
2. Synchronously `bind(readyAccount)` or `bind(null)` as the provider publishes/fences a session. Null hides and retains same-owner edits; a verified different owner clears them.
3. Include `hasUnsaved()` in sign-out and beforeunload guards, and clear only after confirmed logout (or verified owner switch).
4. Pass the memory instance to each controlled tool editor.

`useStandaloneWorkspace({ codec, emptyPayload, memory })` exposes `status`, `payload`, `workspace`, `imports`, `dirty`, `pending`, `busy`, `error`, `canEdit`, `canSave`, `setPayload`, `importProject`, `save` and `reload`. Private fields disappear while unverified. Every response is fenced by owner, verified account generation, memory binding, request identity and cancellation. New tool reads initialize only after the owned GET succeeds. An import is an explicit read/projection into the unsaved draft. Active imports disable concurrent edits. Uncertain saves retain the original body/key, disable editing and permit exact retries. Conflict recovery requires an explicit `reload(true)` discard choice; automatic reload never drops dirty/pending input. A 409 retains edits and requires explicit recovery; failed reads/imports do not manufacture success.

The shared provider's actual lifecycle wiring and rendered tool acceptance are separate owned integration patches. This slice's automated checks cover the store/client, service/API and database; it does not claim signed-in browser or multi-tab UI acceptance.
