## Exact new lane

`identity.logo_vector_propose` uses handler `logo-vector-propose-v1`, independently configured `logo-vector-propose-api-v1`, model `gpt-6.1-sol`, and the frozen `textPolicy`. The descriptor contains no top-level subscription `policy` or `billingMode`. The six-operation manifest rejects duplicate/foreign operations, and only this exact operation can carry a text policy. The existing concept, raster refinement, vectorization, directions and export adapters are unchanged. The raw raster `vectorRefinement: null` limitation remains. Generic Strategy/API/subscription workers are not expanded. The new operation produces retained proposal intent only; authenticated zero-AI candidate creation and explicit acceptance are separate work.

## Dedicated configuration

The existing protected `logo-worker.json` format accepts an optional `operations.proposals` exact descriptor paired with an independent `vectorProposal` object containing `operation`, `paidCallsApproved: true`, `textPolicy` and an explicitly supplied `apiKey`. The capability policy and configuration policy must match exactly. No default policy, image approval, reformulation setting, environment credential discovery or alternate provider can enable it.

A proposal-only configuration omits `storage` and `image`. It does not create storage brokers, image/vector/rendering runtime qualification, asset adapters or font capabilities. Existing asset lanes still require their exact storage configuration; an unused storage session is rejected in proposal-only mode. One launcher, one checked connection/pool owner, one runtime/readiness owner and one polling loop remain. The existing protected-file safety checks and redacted opaque configuration handles are preserved.

## Evidence and shutdown

Production startup composes the accepted four database ports with the passive reviewed adapter. The JobStore permits only the new exact step and typed prepared/unpublished evidence; the existing failed partial-export exception is unchanged. SQL remains authoritative for original dispatch authority, immutable receipts, known charges, settlement and late callbacks. Completion does not add a second charge. For a proven over-cap unpublished outcome, the JobStore restores the frozen envelope reason after the shared runner rewrites its outer code; full observed expense and bytes remain unchanged, and SQL independently keeps reconciliation. The customer reservation stays capped while actual provider expense remains fully recorded.

Closing synchronously fences new work and the provider's final physical dispatch fence. Already dispatched proposal executions are now tracked separately from the runner tick: if a cancellation grace or deadline ends first, the host keeps its checked connection available until observation/staging settles. A known late bill and bounded output therefore can reach the reviewed SQL recovery path after terminal uncertainty. The launcher must not dispose its pool or report a confirmed drain until the host closes successfully.

A pending application promise is not proof that native processes or network activity ended. An uncooperative injected transport can keep the close promise pending; there is no forced cleanup, permission to restart, automatic inference retry or claim of universal shutdown. The normal provider and checked SQL transports retain their existing deadlines. Live provider, native Postgres session/pooler concurrency and process supervision remain activation qualifications.
