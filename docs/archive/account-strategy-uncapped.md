# Managed uncapped Strategy contract (unapplied)

The future managed Strategy worker uses `hosted_strategy_owner_uncapped_v1`, with explicit `spendControl: "uncapped"` in its approved profile. It reuses the existing durable API text queue, runner, guided handlers and Responses request format. Existing bounded, subscription and local contracts remain separate. This source change does not install a database packet, approve a profile, start a process or call a provider.

Apply order for a separately reviewed deployment is the existing migrations, `supabase/candidates/account_service_enrollment.sql`, `supabase/candidates/account_worker_enrollment.sql`, then `supabase/candidates/account_strategy_uncapped.sql`. Provisioning requires the two new owner facades to exist. Installation creates no account, credit or allowance cohort. The first qualified uncapped admission creates a missing owner bookkeeping row with all monetary values zero, under the existing owner lock; it never changes an existing account or funds credits. Zero is not a spending allowance and cannot authorize bounded work. Runtime startup can qualify the managed principal before this first bookkeeping row exists. The explicit profile may select an absent OpenAI billing route; an existing subscription route is a conflict. Provider, runtime artifact, managed role, model, policy and fresh worker qualifications remain independently required.

The authenticated owner facades are `get_managed_strategy_availability(project_id)` and `enqueue_managed_strategy_job(project_id, expected_revision, operation, idempotency_key, accepted_policy_identity)`. The ordinary Strategy availability RPC delegates only for the explicitly approved managed profile. Availability returns the approved policy identity and uncapped mode; admission accepts that identity instead of a dollar ceiling. Immutable input version 3 contains the context, policy, frozen assistant history, policy identity and uncapped mode. Versions 1 and 2 retain their exact formats and hashes. The queue message remains version 1.

An exact private transaction witness permits admission. A separate immutable job marker binds the owner, project, input hash, role name/OID, deployment, policy and enrollment generation/revision/operation key. The restricted SQL claim returns an authority sidecar bound to the actual claimed lease and immutable input. The store retains authority for that specific claimed object; an input property, copied job object or process option cannot grant it. This authority bypasses monetary affordability and over-estimate classification only. Existing price estimates, reservations, actual costs and settlement evidence are retained as bookkeeping. It does not change an account limit, create credits, or add a monetary ceiling.

Policy and provider configuration, owner isolation, deletion, one active Strategy request per project, saved turn/history validation, idempotency, claim attempts, lease, Stop, token/tool/time limits, response/source validation and unknown-outcome fences remain enforced. New admission and dispatch close on ban or revocation. Already-issued accounting observations use the existing narrowly qualified observation lane; they cannot begin a request, dispatch, retry or authorize Storage. Unknown provider outcomes still prevent further paid work. A known cost above an estimate alone does not turn a known outcome into an unknown outcome under the new contract.

Offline validation uses disposable PostgreSQL-compatible SQL and actual restricted session authorization, with inert provider responses. It covers all four registered operations at zero allowance and preexisting spend; all four above-estimate cost receipts; immutable v3 input/hash and exact replay; absent/forged claim authority; owner, revision, policy and lease denial; default ACL cleanup and changed predecessor refusal; Stop and post-ban receipt retention; and continued unknown-outcome blocking. API tests cover exact uncapped fields and refusal to fall back to bounded admission when the new facade is missing. Saved v1/v2 input and request hashes were compared with the original repository implementation. These checks do not establish hosted startup or live provider quality/readiness.
