# Naming Brain Implementation Plan

> Historical managed-Agents implementation plan. The [current project rules](../../../AGENTS.md) supersede its mandatory subskills, fixed monetary caps, task-specific approval holds and preservation requirements for disposable test data. No particular subskill or original staffing split is required by this record. [Fast-first Naming](../../naming-fast-first.md) describes the newer initial generation flow; use current rules for model selection, design and publication. The original contracts, amounts and test cases below remain dated implementation evidence.

**Goal:** Deliver one account-owned Naming workflow with approach widgets, sourced creative exploration, 100 distinct initial names, feedback, and automatic scrolling continuation.

**Architecture:** Keep Next.js as the authenticated interface and the existing Node worker as the durable executor. Version the existing `naming.generate` operation for the managed-agent pilot; reuse ownership, leases, reservations, immutable outputs, and exact-request recovery. Five specialist roles exchange validated saved records, with independent Creator assignments and application-owned publication.

## Historical implementation corrections — 2026-10-16

These corrections record the original managed-runtime design, including the separation of output completion from final accounting. Later local and hosted runtime changes are documented in their dated verification records. The historical caps below are not spending limits for new work. Current task and standing authority come from the user's instructions and [project rules](../../../AGENTS.md).

- Output completion and final accounting are separate. The original pilot retained each full admitted allowance until verified reconciliation; its historical values appear below. Public `confirmedActualCostMicrousd` stays null until known. Native counters, caps and token estimates are provisional observations and cannot replenish allowance. Ordinary provisional billing does not fail valid completed output; unknown execution identity/dispatch or observed overrun blocks new paid work. Proven never-dispatched cancellation can reconcile verified zero. Model tools cannot submit financial settlement evidence.
- Use one fresh managed session per validated Creator assignment, native delegation disabled, tools empty and `environment.type: "none"`. A caller-controlled pool runs at most three concurrently. Freeze assignment caps before dispatch so their sum is at most 150 cents; initial target counts in cents provide this allocation when they sum to 150. Do not re-lend unconfirmed unused caps. Split the gap stage's 75 cents across its calls before dispatch. Bind output to real session/root-turn/final-item and assignment evidence; do not invent child IDs.
- Research and Verification use a narrow root-only `read_reference` function: reviewed exact public HTTPS hosts, no redirects/authentication/cookies, checked public DNS destinations pinned to the connection, bounded bytes/deadline/cancellation, and nonexecuting parse5 extraction. Retain response/text hashes and exact nonempty quoted spans tied to real run/item observations. Native search URL metadata alone does not establish textual support. Unsupported or blocked sources remain unknown.
- Scope the complete V2 Naming lifecycle: claim, heartbeat, manifest, begin, dispatch, receipt/artifact persistence, completion, finish, expiry/recovery and project stop/delete guards. Exclude V2 from generic claim and expiry and existing Strategy/legacy consumers. Preserve `jobs.policy_identity = NULL` for API jobs; freeze accepted policy identity in run/input/batch. No generic role/admin fallback or raw-table grant may bypass this boundary. Guard shared settlement against refunding unknown V2 liability. Generic runner numeric cost fields contain only confirmed subtotals, never final V2 expense; scoped dispatch bounds remain independently enforced.
- `EnsureNamingRunIntent` uses `version: 1`, `expectedDemandSequence`, expected project/preference/steering revisions, `consumedThrough: { entryId, position } | null`, and a stable idempotency key. Ordinary reasons are `initial | scroll`; explicit `resume` additionally binds `resumeOfRunId` and `expectedRunRevision`. The feed returns demand sequence; runs return revision and nullable resumed parent. Ordinary scroll never recreates terminal partial/cancelled demand. Explicit Resume coalesces one new linked run with a fresh snapshot and allowance. Safe crash recovery retains the existing run and allowance; known in-flight sessions enter observe/reconcile-only recovery, and missing create IDs never permit a replacement create.
- Fence exposure by material Strategy key, preference and steering revisions; incidental project changes such as selecting a name do not invalidate the creative basis. Keep raw/unused/partial candidates in private artifacts. Only validated prepared/feed candidates enter the shared candidate table.
- Register Naming memory with `src/components/workspace/account-session.tsx` to preserve exact pending writes through same-account verification and clear them on confirmed logout or owner change. The correct lifecycle suite is `tests/client/account-lifecycle-provider.test.ts`.
- Stop applies to the exploration head, including admission whose acknowledgement has not arrived. Persist `paused` and fence an idempotent Stop with the observed demand sequence and nullable pending ensure key; a receipt-bound exception handles a lost explicit Resume acknowledgement without rebasing to unrelated new work. Explicit continued exploration consumes eligible prepared membership without a new reservation; incomplete terminal work creates the previously specified new linked run. A paused head with no run requires explicit Continue, never scroll. Job-only cancellation remains a distinct operation.
- Strong steering changes direction while preserving the paused head and Stop epoch; it does not itself resume exploration. Gap work freezes an ordered phase envelope before gap I/O: direction 10 cents, creation 40, curation 5, verification 20, with all eight allowed searches in verification. Exact call hashes freeze phase by phase after previous saved outputs exist. The total remains 75 cents, with no cap re-lending, retry or additional round.

**Tech Stack:** Existing TypeScript, Next.js 16.3.8, React 19.3, Zod 4, Supabase/Postgres, dedicated Node worker, Vitest/PGlite, and dedicated headless Playwright. Use the public OpenAI Agents API for the isolated pilot with `environment.type: "none"`; use its official supported TypeScript SDK behind a narrow transport adapter.

## Original implementation constraints

- Initial generation delivers 100 names. The grid continues automatically as the user scrolls, with advance generation and a bounded buffer. Ordinary exploration does not require a Regenerate action.
- Allocation is flexible, with every selected approach represented. Equal quotas are not required.
- Review uses curated exploration. Unusual names with potential remain eligible; the reviewer's personal taste is not a removal criterion.
- Every generation batch includes a modest research pass, with deeper verification for language, origins, and cultural references.
- Likes gently influence upcoming generation. More like these supplies stronger direction while preserving variety and room for unusual names.
- Three concurrent Creator assignments at most; roughly 150 initial raw candidates; five distinct primary credits per selected approach. One optional replacement round contributes at most 50 additional raw candidates within the same reservation.
- Strategy, including personality, is inherited. Unknown facts stay unknown. Persist acknowledged account saves before admitting context-dependent work.
- Keep operation/storage/service identifiers and historical records compatible. Prepare additive SQL only; live application of migrations, new credentials, activation, deployment, and pushes require their applicable existing authority.
- This plan does not fund ordinary accounts or change existing Strategy allowances. Runtime admission uses the actual operation policy, not an old conversational spending approval.
- Preserve disjoint ownership and unrelated changes. Specialists do not commit or push; the integration lead owns the verified checkpoint.
- Use the approved Embel shell and tokens. Read installed Next docs before code changes. Keep Namelix materials in ignored references; implement original code, and never call its services as Embel dependencies.
- Source/role/model output is untrusted until validated. UI imports no privileged modules; all ownership derives from verified authentication and database enforcement.

## Review Focus

1. Repeated scroll events, two tabs, and restored scroll positions must not admit duplicate or runaway paid work (Tasks 2 and 5).
2. A late result after account or steering changes must not enter the current feed or lose the original saved work (Tasks 2, 4 and 5).
3. False source claims must not become verified facts; unusual but valid names must survive taste-based curation (Tasks 1, 3 and 4).
4. A failed acknowledgement after provider dispatch must preserve identifiers, costs and results without repeating inference (Tasks 3 and 4).
5. Long project history must not overflow prompts, silently lose duplicate coverage, or erase legacy provenance and workshop replay (Tasks 1, 2 and 6).

## Interfaces fixed by this plan

- Keep operation `naming.generate`; new immutable job input is `NamingBrainJobInput` with `version: 2`, `handlerVersion: "naming-brain-v1"`, `billingMode: "openai_api"`, owned `runId`, `jobId`, a `NamingBriefSnapshot`, and an accepted policy identity. Legacy inputs/results retain their existing discriminants.
- `NamingPreferencesV2` retains the existing locale/notes/grapheme fields, with `version: 2`, `approaches: NamingApproach[]`, `directness: NamingDirectness | null`, `sourceLanguages: string[]`, `heritageNotes: string`, `culturalNotes: string`, `requiredText: string[]`, and `excludedText: string[]`. Empty choices are valid saved drafts but not generation-ready. Do not infer selected cards during legacy reads.
- Approaches: `real_words`, `compounds`, `blends`, `invented`, `modified`, `phrases`, `initials`, `other_languages`, `classical_roots`, `people_places`, `stories_culture`. Directness: `direct`, `suggestive`, `open_ended`, `all`. Cards are multi-select; directness is one choice.
- Required/excluded fields describe text fragments, compared case-insensitively after NFC normalization. Label this meaning in the optional controls; do not substitute stemming or fuzzy word matches. Existing Unicode name-identity/grapheme semantics remain unchanged.
- `NamingBriefSnapshot` binds the project/Strategy and preference revisions, feedback and explicit steering revisions, selected approach IDs, source preferences, current strong seed IDs, and bounded recent/liked examples and pattern summaries. The database, not the model prompt, owns the complete history index.
- Role result types: `NamingResearchPack`, `NamingAssignmentPlan`, `NamingCreatorSet`, `NamingCuration`, `NamingVerification`, `NamingPreparedSet`. Every artifact binds `runId`, `stageKey`, snapshot hash, schema/prompt version, and server-recorded provider receipt. Models supply local reference keys; the server resolves owned records and assigns persistent IDs.
- `NamingRoleOutput` is the union of the five role outputs above; `NamingPreparedSet` is application assembly output. `NamingAssemblyInput` contains `snapshot`, validated `candidates`, `curation`, applied `verification`, and `existingIdentityKeys` returned by a complete-index lookup for those candidate identities. The output contains `targetCount: 100`, ordered candidate IDs, per-approach primary counts, retained unused IDs, actual fulfillment, and explicit deficits.
- Each candidate has one `primaryApproach`, optional additional selected approach tags, a `territoryId`, a displayed value, concise rationale, optional concrete caution, and claim references. A factual claim records its exact statement, supporting source references and verification status; creative interpretations stay identified as interpretations.
- `NamingAgentRuntime.runStage(request: NamingStageRequest, hooks: NamingStageHooks): Promise<NamingStageOutcome>`, `resumeStage(receipt: NamingProviderReceipt, hooks: NamingStageHooks): Promise<NamingStageOutcome>`, and `cancelStage(receipt: NamingProviderReceipt): Promise<void>` form the provider seam. Outcome is completed, rejected-before-dispatch, or unresolved; a disconnected stream is not completed or cancelled by assumption.
- `NamingStageRequest` contains `runId`, `stageKey`, `role`, `snapshotHash`, validated `input`, `dependencyArtifactIds`, `requestKey`, and the server-derived role policy. `NamingStageHooks` contains `signal`, `beforeDispatch()`, `onReceipt(receipt)`, and `onArtifact(rawCompletedItem)` callbacks, all awaited. `NamingProviderReceipt` binds the stage/request to real session/turn/agent/call IDs when known, observed model, tool/usage records, and known actual cost. Completed `NamingStageOutcome` carries a receipt and typed output; unresolved carries any known receipt and retained partial artifacts; rejected-before-dispatch carries an operational code and no inferred spend.
- Authenticated services: `getNamingFeed(auth, projectId, cursor?)`, `ensureNextNamingRun(auth, projectId, intent)`, `steerNamingFeed(auth, projectId, intent)`, `getNamingBrainRun(auth, projectId, runId)`. The body never supplies ownership, provider output, or an arbitrary cost/model policy.
- `EnsureNamingRunIntent` carries expected project/preference/steering revisions, the owned consumed-through candidate/feed cursor, reason `initial | scroll`, and a stable idempotency key. Result is a discriminated `NamingFeedEnsureResult`: saved names appended, an existing/new pending run, paused/blocked, or an actionable incomplete state. Strong steering is its own mutation with one to five owned candidate IDs and optional instruction.

### Historical initial pilot policy

The table records the original policy design, not defaults to restore or permission to spend. Accepted policy identities are immutable for admitted requests; configuration changes apply prospectively. Model and reasoning choices are not prescribed by this plan, and unavailable configuration must not trigger a silent provider/model fallback.

| Stage | Maximum reservation, USD cents | Additional bound |
| --- | ---: | --- |
| Research | 75 | Four web-search calls |
| Direction | 25 | No web/MCP tools |
| Creation | 150 | Three concurrent independent managed sessions, 150 raw candidates total |
| Curation | 50 | No web/MCP tools |
| Verification | 125 | Twenty web-search calls; claims without support stay unresolved |
| Gap | 75 | One round, fifty additional candidates, eight search calls including its verification |
| Prepare | 0 | Application/database work only |

The original policy specified a US$5 reservation per run, shared across sessions/children, and a US$25 aggregate pilot ceiling. Money contracts use integer micro-USD: one cent is 10,000 micro-USD. That policy also specified a 131,072-byte role-input bound including instructions, 524,288-byte completed-output bound, and 240,000 ms stage deadline. These historical values do not replace the current versioned runtime policy. Search counts refer to actual recorded search invocations; the adapter also bounds retained source/item bytes and cancels on exceeded limits. Provider overshoot or unknown usage is retained for reconciliation, never silently charged to a new reservation. These caps can yield an honest partial set; they do not justify fabricated facts or filler.
