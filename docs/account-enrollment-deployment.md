# Account enrollment release packet — unapplied source

> Historical per-customer candidate. The current shared design is documented in
> [shared-worker-pool.md](shared-worker-pool.md). Keep this packet as review and
> compatibility evidence; use the shared configuration for new deployment planning.

This packet adds automatic confirmed-customer enrollment for five capabilities: Home attachments, Identity transactions, Strategy, Naming and Logo. The Auth trigger writes durable intents; a separate restricted reconciler provisions owner-bound SQL principals, reserves durable credentials, publishes bindings and verifies actual runtime authority. `ready` requires all five independently verified capabilities. HTTP-only success remains `pending`.

No candidate in this packet has been applied to the hosted application. No production login, grant, account, service actor, Vault backend/token, approved profile, supervisor, provider call, deployment or feature flag was created by this work. The current source is a release candidate, not evidence of production readiness.

## Least privilege and credentials

`embel_account_role_manager` is NOLOGIN/NOSUPER/NOINHERIT/CREATEROLE/NOCREATEDB/NOBYPASSRLS/NOREPLICATION. It owns only narrow fixed create/disable/grant functions and has grant option only for database CONNECT/TEMP, schema USAGE and enumerated reviewed helper EXECUTE. It has no customer/Auth/Storage/enrollment table privileges or schema CREATE after installation. Its sole incoming membership is the existing trusted `postgres` ADMIN=true, INHERIT=false, SET=false edge. Its only outgoing edges manage the exact recorded child roles with the same admin-only attributes. Native PG17 testing proves this edge cannot `SET ROLE` to a child.

Each customer gets separate capability logins, hard-derived from the locked lease owner: `embel_home_web_<uuid32>`, `embel_identity_web_<uuid32>`, `fluid_api_text_worker_<uuid32>`, `fluid_naming_brain_worker_<uuid32>`, `fluid_logo_worker_<uuid32>`. Role OIDs, owner, generation, revision, capability and operation key are independently verified. Legacy and development principals keep their original stricter membership checks.

## Durable store, publication and service host

The concrete optional adapter supports Hashicorp Vault KV-v2 over an explicitly supplied canonical HTTPS origin/mount/token. No backend is selected or created by the source. An approved compatible store/service and explicit access policies are external prerequisites.

- The provisioner needs read/CAS-create/update only on its chosen credential/publication namespaces, plus KV-v2 destroy on prior secret versions when retiring credentials. Reservation uses a stable owner/generation/capability/operation reference before SQL effects and returns only an opaque reference and SCRAM verifier to SQL. Plaintext database/provider/Storage credentials stay in the approved store and process memory.
- The web reader uses a **different read-only token** restricted to HTTP credential and HTTP publication paths. It has no worker/provider paths, write, CAS, destroy, role-manager or reporter authority. Its owner-derived Auth RPC must match generation/revision/operation/publication receipt before a privileged pool can be opened. Pool cache size bounds active entries, not total enrolled customers; idle entries evict, in-flight requests release normally, and stale evidence retires old pools.
- Public worker process descriptors contain only owner/generation/revision/capability/operation identity, approved profile/artifact metadata and opaque credential references. Protect descriptor directory integrity and atomicity; no password, provider key or Storage token may enter files, logs, SQL/public status or Queue messages.
- The separately started `createConfiguredAccountEnrollmentService` in [service.ts](../worker/account-enrollment/service.ts) composes the fixed SQL operator, durable CAS store, monotonic HTTP publisher, HTTP/worker adapters, isolated process controller and existing verified Queue SDK callback. Its trusted host must supply configuration and own child supervision/drain. Importing or constructing the service is not deployment or readiness.
- Build/qualify the per-owner worker artifact with `npm run build:account-worker`, pinned Sharp/runtime, source/artifact hashes, clean reviewed source, actual project/deployment metadata and exact approved provider/model/policy profile. Naming uses `hosted_owner_v1`, provider budget version 2 and explicit `uncapped`; Logo uses `account_logo_operation` and explicit `uncapped`. The source never substitutes a capped/local-prototype admission lane for those contracts. Strategy uses the separately reviewed `hosted_strategy_owner_uncapped_v1` profile, facade and version-3 input/policy witness; its approved per-operation policy and billing route remain required.
- The verified Strategy Queue trigger and long-running supervisor must be separately configured. Missing store, profile, reporter, process, actual heartbeat, provider route or Logo Storage session stays blocked. A supervisor crash cannot manufacture a stopped-process receipt.

Completed enrollments are periodically leased again using the same generation/operation keys and the existing 60-second available-at schedule. Worker adapters may implement `maintain` to inspect the actual owned child, fresh SQL heartbeat/reporter evidence and existing actor authority. Maintenance does not create roles, credentials, jobs or provider dispatches. Failed maintenance closes admission independently of the retained completion phase; observation/receipt authority remains intact. Only a known exited/stopped and drained child can be recovered under the existing fenced engine. A missing handle after an unobserved supervisor crash remains blocked for trusted recovery. HTTP continues to qualify at request time.

## Service actor ordering

A Logo Storage actor is distinct from its customer. Create it **unconfirmed** using an independently approved Auth administrator flow. Before confirmation, the reviewed lease-bound `register_account_worker_storage_actor` operator RPC derives the customer/Logo operation from its lease and immutable approved profile and calls the private `account_worker_register_storage_actor` to atomically register the `account_service_actors` exclusion marker and narrowly scoped Storage approval. The wrapper also pins server-only Auth app metadata to the exact enrollment, operation and durable reservation; user metadata is ignored. Registration rejects already-confirmed users and any existing customer work. Then confirm through the approved Auth service. The Auth outbox sees the exclusion marker and never enrolls that actor as another customer. User-editable metadata is never an exclusion authority. Existing already-confirmed service identities require an explicit reviewed transition; do not silently relabel them.

## Startup flags and revocation

All new flags default off. Only after reviewed installation/configuration and acceptance should a release enable `EMBEL_ACCOUNT_ENROLLMENT_ENABLED=true`, `EMBEL_ACCOUNT_HTTP_SOURCE_ENABLED=true` with server-only `EMBEL_ACCOUNT_HTTP_SOURCE_CONFIG` (`vault`, `publicationPrefix`, `credentialPrefix`), and, for the managed Logo route, `EMBEL_MANAGED_LOGO_ENABLED=true` with its strict production deployment gate. No example includes real values. The old bounded static `EMBEL_ACCOUNT_HTTP_BINDINGS` registry is an interim manually configured capability, not automatic signup enrollment. A configured but invalid dynamic source fails closed without static/development fallback.

Ban, deletion, suspension or service-actor exclusion invalidates the lease/revision and immediately closes managed admission. The Home restrictive policy denies managed Home Storage authorization even with stale JWT claims; it cannot broaden any existing Storage policy. Legacy unmanaged Home and non-Home policy behavior is preserved. HTTP bindings withdraw monotonically, logins become NOLOGIN/PASSWORD NULL, and proof waits for existing active/idle-in-transaction sessions to drain. No HTTP backend is killed. An uncommitted transaction paused before its final owner helper may fail closed and roll back after revocation; completed receipts and immutable commit history remain recoverable through ordinary owner-read APIs. The verifier pins exact Storage helper body/metadata/ACL and restrictive policy and proves **SQL Storage authorization denial**, not a performed HTTP Storage request. Missing statistics visibility or an active/unknown transaction leaves revocation pending.

Workers revoke in two stages: stop new claims/begins/dispatch and close Storage admission first, retaining exact prior own-session observation/lease identity for issued-provider receipts, accounting, unknown outcomes, cancellation and durable cleanup. Only a fresh independently registered stopped-process report, drained job leases and Storage denial allow NOLOGIN/PASSWORD NULL and the final revocation witness. Auth 403, pointer withdrawal, an expired heartbeat or an absent process handle alone is insufficient. A never-provisioned worker operation instead requires the separately scoped SQL proof `scope: never_provisioned` / `authorityAbsent: true`, with no `runtimeStopped` field. That branch proves current-generation SQL/job/Storage authority absent and any reserved Auth actor absent or banned with no live sessions/refresh authority; it never invents a stopped process. Recovery cannot publish a prior generation over a ban; reactivation starts a fresh generation with new operation keys and does not reuse another owner's binding.
